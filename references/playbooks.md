# 典型工作流剧本

每个剧本 = 分工 + 任务包序列 + 验收点。执行时套用 SKILL.md 的任务包模板，别照抄示例文案。
**统一方向**：方案由顾问组多轮互审到最详细版（方案阶段多审一轮，干活组返工少一轮）→ 干活组只制作/修复 → 组长实测验收 → 用户终验。

## 剧本 A：编码工程（如 DSH 插件、YASB 组件、工具脚本）

**分工**：组长拆任务 → 千问类顾问主笔方案 → 豆包类顾问互审（多轮）→ 最详细版定稿 → 干活组实现落盘（现役 DSH，可换 Codex/Claude Code 等）→ 组长验收 → 有 bug 走修复循环。

1. 组长明确需求 → T01「出方案任务包」派**千问**：输出具体技术方案（技术选型、模块划分、数据结构、文件清单、接口、风险点），不写实现
2. T02「互审任务包」派**豆包**：逐节审可行性/遗漏/歧义，输出意见清单；千问按意见完善 → 多轮往返直到无实质分歧（常规 3 轮起步）
3. 主笔做「实现者视角自检」后定稿，组长裁决残余分歧
4. T03「实现任务包」（附定稿方案全文）派 **干活组**（现役 DSH，可换 Codex/Claude Code 等）：直接落盘 + 自测 + 交交付说明.md
5. 组长验收：Read 文件、语法检查、实际运行、逐条过方案验收标准，出验收报告
6. 有 bug：组长出问题清单 → 顾问组出修复方案 → 干活组修复 → 组长复验（循环，同一问题 3 轮上限）
7. 交付：产物文件 + 改动摘要 + 遗留风险

**验收点**：代码必须在本机实际运行过；干活组全程没有输出过方案、没有做过设计决策（发现即打回）。

## 剧本 B：自媒体内容（抖音/公众号）

**分工**：豆包主笔选题与文案 → 千问互审（多轮）→ 组长按用户口径定稿 → 需要成品（网页/PPT/播客）时派干活组（现役 DSH，可换）制作；ima 供弹药。

1. ima：公众号素材/过往爆款入库后 @知识库 问答，产出选题素材包
2. T01「选题任务包」派**豆包**：结合素材包出 5 个选题（含切入角度、目标人群、标题备选）
3. 用户/组长选定后 → T02「初稿任务包」派**豆包**（口播语感）或**千问**（长文）撰写，**严格基于素材，禁止编造数据**
4. T03「互审任务包」派另一位顾问：语感/事实/结构多轮互审 → 最详细版定稿
5. 组长按用户口径定稿（常见口径：不增内容、保留原稿原话、页数精简——PPT 类可直接走现成 PPT 技能）
6. 成稿回存 ima 知识库（形成闭环）

**验收点**：所有数据可溯源；文风过「用户口径」检查；成品制作前方案已定稿，干活组不参与文案决策。

## 剧本 C：知识调研（合同/研报/竞品）

**分工**：组长采集/精读（或派千问长文精读）→ 千问主笔报告 → 豆包类顾问互审（多轮）→ 组长合并交付。

1. T01「精读任务包」派千问（长文本强项）：全文解析，输出结构化摘要 + 关键条款/数据 + 疑点清单
2. 材料入库 ima（后续可问、可溯源）
3. T02「报告方案+成稿任务包」派千问：基于摘要与素材起草报告提纲+正文（免费额度承担成稿）
4. T03「互审任务包」派豆包：结论是否有数据支撑、结构是否服务读者、表述是否口语化失真——多轮互审到定稿
5. 组长合并成交付物（对比表 + 结论 + 建议）；需要成品文件时派干活组排版落盘
6. 大规模并行采集由组长代跑（原 Swarm 通道已停用）

**验收点**：每个关键结论标注来源文档/条款号；引用可溯源。

## 剧本 D：本机文件/系统任务（特殊工作组启用）

**分工**：组长拆解 → Marvis 执行 → 组长复核。

1. 触发条件：批量文件整理、系统排查、跨端（手机↔电脑）接力，且组长直接做不便或越权
2. 组长生成「执行任务包」给用户带进 Marvis：目标 + 范围（明确哪些目录）+ 禁止事项（如「只整理不删除」）
3. Marvis 执行中高风险动作会请求确认——**用户确认，组长不代确认**
4. 完成后组长抽查结果（Read/Glob 验证文件真的归位）

**验收点**：涉及移动/删除的操作，先备份再动手；结果抽查 ≥ 10%。

## 剧本 E：带数据库的网站

**分工**：千问主笔站点方案 → 豆包互审（多轮，重点审数据模型与边界情况）→ 定稿 → 干活组生成站点落盘 → 组长拉起实测。

1. T01「站点方案任务包」派**千问**：页面结构、数据模型、接口约定、技术栈（默认无构建、file:// 可用或明确部署方式）
2. T02「互审任务包」派**豆包**：技术可行性与兼容性意见清单 → 千问完善 → 多轮互审到最详细版
3. T03「实现任务包」派 **干活组**：按定稿方案生成站点（含数据库脚本/初始化数据）落盘
4. 组长拉起预览、走查功能、验证数据读写，逐条过验收标准
5. 有 bug 走修复循环（组长问题清单 → 顾问组修复方案 → 干活组修复 → 复验）
6. 交付：链接/文件 + 功能清单 + 数据说明

## 通用规则（所有剧本）

- 每个子任务建 TaskCreate 跟踪，状态实时更新
- GUI 客户端（千问/豆包）派发 = 拉起进程 + 剪贴板任务包 + 交代用户粘贴；不要等进程「跑完」；Cua Driver 接入后可自动投递
- 干活组（DSH/Codex/Claude Code 等 CLI）可组长直接 shell 调用并收产物（落盘交付）
- 方案永远顾问组主笔+互审（多轮，以无实质分歧为退出条件）；干活组每轮输出只能是「实现产物+交付说明」或「修复产物+交付说明」
- 验收永远组长实测（不轻信交付说明），用户是最终验收人；交付永远由组长完成，产物文件用 present_files 呈现
